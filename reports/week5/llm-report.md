# LLM Usage in FaceGuard Project — Assignment 5

During Sprint 3 (Assignment 5), Large Language Models (LLMs) were utilized for the following tasks:

1. **Architecture Documentation:** Drafted the maintained architecture artifact at `docs/architecture/README.md`, including the section structure for the static view, the dynamic view, and the deployment view. LLMs proposed initial PlantUML skeletons for the component diagram, the registration sequence diagram, and the deployment diagram, which were then reviewed and adjusted to match the real FaceGuardV2 service boundaries, ML client, `FaceDatabase` DAL, and servo abstraction.

2. **Architecture Decision Records (ADRs):** Generated the Context / Decision / Consequences / Related views structure for ADR-001 (separate backend and ML service), ADR-002 (SQLite through `FaceDatabase` DAL), ADR-003 (session auth and password hashing), and ADR-004 (servo abstraction with emulated mode). LLMs helped articulate the tradeoffs (for example, the runtime dependency on ML service health in ADR-001 and the SQLite scalability limits in ADR-002) and linked each ADR to the corresponding Assignment 4 quality requirements.

3. **Development Process and Configuration Management:** Drafted `docs/development-process.md`, including the process overview, the Work Status table, the Definition of Done reference, the secrets handling section, and the CI process description. LLMs also produced the Mermaid `gitGraph` diagram from the real branch and PR history (`58-fix-the-mvp-v1`, `65-optimizing-product`, `LLM-report`, `presentation`, `PR #64`, `PR #66`, `PR #73`, `PR #74`, `PR #75`) and the narrative explanation of the transition from descriptive branch names to issue-numbered branch names.

4. **Backend Refactoring (Unified Users Table):** Assisted in designing the schema unification of `users` and `guests` into a single `users` table with a `type` field (`permanent` | `temporary`) and a nullable `expires_at` column. LLMs produced the initial SQL migration logic and the `FaceDatabase.update_user()` implementation, including the rule that switching a user to `permanent` automatically nullifies the expiration field. The legacy two-table auto-migration path on startup was also drafted with LLM assistance.

5. **Liveness Detection Implementation:** Supported the design of the active anti-spoofing mechanism based on eye blinking. LLMs surveyed existing liveness approaches (passive texture analysis, frequency analysis, active challenge-response) and recommended the randomized-timer blink challenge as the most appropriate choice for the CPU-only Raspberry Pi target. The implementation of the 1–3 second randomized prompt and the rejection of static photographs (even when shaken) followed this design.

6. **Test Generation:** Generated test scaffolding for `tests/test_crud.py` (30 unit tests covering the unified schema, CRUD operations, type switching, log rotation, and transition-only logging) and `tests/test_crud_api.py` (21 integration tests for the new `GET /backend/users`, `GET /backend/users/{id}`, `PUT /backend/users/{id}`, and `DELETE /backend/users/{id}` endpoints, the HTML detail page, and validation paths for type, `expires_at`, embedding size, and duplicate names).

7. **Audit Log Optimization:** Designed the transition-only audit logging behavior in `FaceDatabase.recognize()` together with the `purge_old_logs(days=30)` retention policy. LLMs proposed the `log_transitions_only` flag (defaulting to `True`) and the daily background invocation from `RecognitionLoop`, which produced a 5–10× reduction in audit log volume.

8. **Model Downsizing:** Supported the migration from `buffalo_l` to `buffalo_sc` in `ml_service/main.py`. LLMs summarized the tradeoff between embedding quality and CPU inference cost on edge devices and confirmed that `buffalo_sc` is the recommended InsightFace model variant for CPU-only Raspberry Pi deployment. Threshold recalibration guidance for the new model was also produced with LLM assistance.

9. **Customer Feedback Analysis:** Analyzed the Sprint Review transcript and the customer review summary to extract the feedback points recorded in `reports/week5/customer_feedback.md`. LLMs mapped each feedback point to the resulting PBI or issue (`#76`, `#77`, `#78`, `#55`) and drafted the response column entries ("Done" for full CRUD and liveness detection).

10. **Sprint Review Artifacts:** Drafted `reports/week5/sprint-review-summary.md` from the recorded transcript, organized into delivered features, limitations and future security enhancements, technical decisions and resource optimization, and hardware deployment and timeline constraints. The Sprint Review notes were structured to cover the Sprint Goal, the delivered `MVP v2` increment, the addressed customer feedback, the UAT results, and the architecture evidence discussed.

11. **Retrospective Artifact:** Produced the structure of `reports/week5/retrospective.md` (What went well / What did not go well / Previous-retrospective follow-up / Action points), including the two action points on sprint capacity estimation (1.5× buffer for refactoring tasks) and mid-sprint integration checkpoints for new recognition-pipeline modules.

12. **Roadmap and Changelog Maintenance:** Updated `docs/roadmap.md` to reflect Sprint 5 (Security & Metrics) and updated `CHANGELOG.md` with the `v2.0.0` entry, organizing the user-visible changes into Added, Changed, and Fixed categories following the Keep a Changelog convention. LLMs cross-checked the issue numbers (`#76`, `#77`, `#78`, `#79`) against the changelog entries for traceability.

13. **Hosted Documentation Preparation:** Assisted in preparing the maintained documentation (`docs/`, `docs/architecture/`, `CHANGELOG.md`, root `README.md`) for hosting on the documentation site, including link validation, section ordering, and consistent cross-references between the architecture README, ADRs, quality requirements, and quality requirement tests.

14. **Sprint Planning and Backlog Refinement:** Supported Sprint 3 backlog refinement by reviewing the open customer feedback points from `MVP v1`, the Assignment 4 quality gaps, and the unfinished architecture work, and by drafting the Sprint Goal ("Harden the system against spoofing attacks and tune the recognition threshold using precision/recall analysis") recorded in `docs/roadmap.md`.

No LLM-generated content was merged into `main` without review. Every LLM-assisted artifact was read, corrected, and approved by a team member before the linked PR was merged, and every code change still had to pass the Assignment 4 CI gates (ruff, ruff format, mypy, Docker build, unit tests, integration tests, QRTs, coverage, `pip-audit`, Lychee) before it was eligible for the `v2.0.0` release.
