# Week 2 Analysis

## Learning points
* **User Stories Design and Decomposition:** During the process of writing user stories, the team learned to separate purely technical tasks from actual business value. We realized that the end-to-end implementation of a single feature can affect entirely different layers of the system. For example, automatic door unlocking requires not only a stable real-time ML recognition pipeline ([US-01](user-stories.md#us-01)) but also seamless integration with physical actuators ([US-06](user-stories.md#us-06)) or their software emulation ([US-07](user-stories.md#us-07)).
* **Balancing Trade-offs in Machine Learning:** Prioritizing [US-08 (Data-Driven Threshold Selection)](user-stories.md#us-08) demonstrated that selecting a similarity/decision threshold cannot be done by guesswork. The team recognized the necessity of gathering a real dataset to plot precision and recall curves. This is essential for establishing a mathematically grounded balance between high security (minimizing the False Acceptance Rate) and user convenience for lab workers (minimizing the False Rejection Rate).
* **Architectural Prototyping (MVP v0):** Developing MVP v0 helped verify the foundational viability of combining OpenCV for face detection and InsightFace for embedding extraction. A crucial lesson learned was that running heavy ML models on a local x86 laptop development environment behaves differently than deploying onto the target Raspberry Pi 5 single-board computer. This highlighted the extreme value of early multi-architecture containerization planning ([US-04](user-stories.md#us-04)) and hardware emulation ([US-07](user-stories.md#us-07)).
* **Insights from Customer Validation:** Meeting with the customer helped us adjust the development focus in time to prevent scope creep. The customer explicitly constrained the operational environment (users must approach the camera individually, one at a time, under basement artificial lighting conditions). This saved the team from over-engineering complex multi-person tracking algorithms or excessive image pre-processing routines.

## Validated assumptions
* **Core Recognition Architecture Stack (Confirmed):** Our technical assumption that a pipeline consisting of OpenCV for face detection and InsightFace for vector extraction would deliver sufficient performance for real-time processing was validated in MVP v0. The customer explicitly approved this implementation approach during our review.
* **Necessity of Physical Feedback (Confirmed):** We assumed that on-screen text overlays would be insufficient for a good user experience. The customer confirmed this assumption and expanded the requirements by suggesting physical LED status indicators (green, red, and yellow) to convey clear access feedback. This reinforced the high importance of both [US-05](user-stories.md#us-05) and [US-06](user-stories.md#us-06).
* **Logging Unknown Intent over Blacklisting (Rejected/Modified):** We initially assumed that managing a malicious blacklist might be necessary for access control security. The customer rejected this approach, adjusting the requirement: instead of active blocking, the system should maintain detailed failure logs ([US-10](user-stories.md#us-10)) and explicitly highlight anomaly patterns, such as when the exact same unknown person repeatedly attempts to gain entry.
* **Multi-User Processing Mode (Rejected):** We were uncertain whether the MVP v1 architecture needed to accommodate multiple faces simultaneously appearing in the camera feed. The customer rejected this necessity, confirming that handling multiple people at once is outside the scope and that users will complete verification one by one.

## Needs clarification
* **Temporary Access Logic Implementation ([US-03](user-stories.md#us-03)):** While the customer approved the requirement to configure access durations during registration (permanent, until a specific date, or for a predefined time period), we need to clarify the exact database and system logic. Specifically, we must determine whether access privileges should expire automatically down to the exact minute, or if a daily cron job checking access records is sufficient.
* **Video Playback Spoofing Tolerance ([US-09](user-stories.md#us-09)):** It was agreed that protection against printed photo presentation attacks is a mandatory requirement for the system. However, we still need to clarify the testing criteria for video playback spoofing attacks using digital screens. We need to know if failing a video playback spoof check will be an absolute blocker for the MVP v1 delivery or if advanced liveness detection can be treated as a future iteration bonus objective.
* **Hardware LED and Raspberry Pi 5 Electrical Specifications:** Since the customer offered to supply the physical LEDs for status indication, we need to clarify their exact technical datasheets (operating voltage, forward current). This ensures we can safely wire them to the Raspberry Pi 5 GPIO pins without risking overcurrent damage to the board.

## Planned response
* **Refining Backlog Priorities and Audit Scope:** Following the customer's request for failed attempt analytics, [US-10 (Failure Mode Audit Logging)](user-stories.md#us-10) will receive increased focus during MVP v1 development. We will design our database log schema to capture not just confidence scores and environmental failure factors, but also structured groupings to audit repeated intrusion attempts by identical anonymous individuals.
* **Decoupling Actuator Hardware via an Abstraction Layer:** To satisfy the constraints of both physical servo actuation ([US-06](user-stories.md#us-06)) and cross-platform debugging ([US-07](user-stories.md#us-07)) without blocking team members who lack physical access to the Raspberry Pi 5 hardware, we will implement a hardware actuator abstraction layer. When compiled on x86 architectures (Windows/Linux), it will trigger a local graphical UI element mimicking the lock behavior; when deployed to the ARM environment via Docker ([US-04](user-stories.md#us-04)), it will seamlessly transition to controlling the physical GPIO pins.
* **Upgrading the User Registration Workflow ([US-02](user-stories.md#us-02)):** Moving away from the hard-coded embedding mocks used in MVP v0, the upcoming sprint will focus on building a robust runtime database registration system. As requested in the approved MVP scope, the registration workflow will capture five distinct face angles to generate a normalized, averaged face embedding. This will maximize recognition accuracy under the specific basement lighting conditions detailed by the customer.
